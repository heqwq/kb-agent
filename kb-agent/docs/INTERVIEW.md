# 面试问答

## Q1：为什么同时用 BM25 和 Dense？单路不行吗？

单路在不同查询上会失灵。BM25 对编号、阈值、专有名词非常可靠，但 test 集里语义型查询的 Recall@5 只有 0.5000；Dense 对口语化改写更稳，但在纯词面查询上并不天然占优。两者失败模式不同，融合的目标是**保住下限**，不是让所有指标无条件上涨。

这组数据也说明一个事实：我们 12 条 test 里 Dense 已经饱和（R@5=1.0），所以 Hybrid 与 Dense 持平，而不是“Hybrid 一定赢”。在 18 条 dev 上，Hybrid 的 MRR 0.8889、nDCG@5 0.9034，高于 Dense 的 0.8704 / 0.8889。真实结论要分切片说，不能拿 dev 的收益去冒充 test。

## Q2：为什么用 RRF，而不用分数归一化后相加？

BM25 分数量纲随查询变化，余弦又在 [-1,1]，跨查询做 min-max / z-score 归一化需要估计分布，容易不稳定。RRF 只用排名，`1/(k+rank)` 对异常分数不敏感，工程上更稳。

但等权 RRF 在这份数据上会被 BM25 的语义噪声拖累，所以我做成**加权 RRF**：

```text
score = w_bm25/(k+r_bm25) + w_dense/(k+r_dense)
```

权重和 k 只在 18 条 dev 上扫，最终选 `k=10, w_bm25=1, w_dense=4`；test 12 条只用于报告。这个“先定参数、再报 test”的顺序要在面试里主动讲清楚。

## Q3：Chunk 为什么是 400–600 字、80 字 overlap？

- 太小：一条制度的条件、例外和数值会被拆开，答案缺上下文。
- 太大：一个块混入多个主题，向量被稀释，引用也不精确。
- 80 字 overlap：主要防止“条件句 + 结论”恰好被切在边界上。
- 先按标题切，再按段落/句子打包，表格整块保留；这样不会为了凑 600 字把句子劈开。

实际语料只有 300–900 字，很多 H2 小节天然短于 400 字，所以会看到 100–400 字的小块。我的实现不是固定窗口，而是“标题内尽量填满”；如果硬把短小节拼成 500 字，标题元数据会失真。这个取舍在 ARCHITECTURE 里也写了。

## Q4：评估集怎么构造的？有什么偏差？

30 条问题，14 条词面型、16 条语义型；固定种子 20261026 做分层抽样，18 条 dev、12 条 test。指标是文档级 Recall@1/3/5、MRR、nDCG@5；Agent 是单跳/多跳成功率、工具链完成率、平均步数、工具调用次数分布、检索 P95。

偏差要说透：

1. 语料是我虚构的 13 篇公司制度，问题也是我写的，不是真实用户日志。
2. 语义型查询依赖 `_DENSE_ALIASES` 同义词表；表与评估集同领域，存在设计者偏差，不能外推到开放域。
3. 12 条 test 太小，一个查询就能改变 0.08 的 R@5，没有置信区间和人工双标注。
4. 词面型/语义型的边界是人工标注，不完全互斥。

这些限制比“R@5=1.0”更值得在面试里主动说。

## Q5：多跳问题怎么处理？现在的 60% 是怎么来的？

`Agent` 是一个 `max_steps=6` 的函数调用循环：模型返回 tool_calls，工具结果以 `role=tool` 回填，直到模型不再调用工具或达到步数上限；每步都有 `TraceStep`。

当前评估用的 `MockModel` 是**规则规划器，最多 3 步**。单跳 15 条全部完成；多跳 5 条中 3 条完成（KB → SQL → calculator 或 SQL → SQL → calculator），2 条需要“先查口径、再查两个数、最后算比例”共 4 步，第 3 步后停止，因此多跳 60%、总体 90%。这是为了验证 harness 的步数边界，不是真实 LLM 的规划能力。接真实模型时，多跳应依靠模型自己分解，或加显式 planner（DAG / ReAct），并把中间结果写入 trace。

## Q6：如何控制成本与延迟？

- 检索：当前小语料 test 集单次 P95 约 1.8–2.5 ms；BM25 和向量都在内存中。
- LLM 成本是大头：控制 `k`、单条片段长度（600 字）、SQL 行数（100 行）、`max_steps`（默认 6）。
- 工具输出加 `result_excerpt`，避免把整段大结果反复塞回上下文。
- 简单事实题优先单次 `kb_search`；比例题才走 SQL + calculator。
- 真实服务应加：查询缓存、embedding 缓存、模型流式输出、按租户限流、失败重试退避。
- 延迟要分 P50/P95 看，不能用 Mock 的 1 ms 冒充生产延迟；报告里 Agent 侧刻意不列 P95，因为那只是进程内规则执行。

## Q7：语料扩大 10 倍，你会先改什么？

1. 向量：线性扫描换成 ANN（FAISS / hnswlib），保留同一 `VectorIndex` 接口；评估召回损失。
2. BM25：单进程倒排表换成 Elasticsearch/OpenSearch 或轻量倒排，支持增量更新。
3. 索引：文档级分片、元数据过滤（部门、密级、时间），权限前置过滤。
4. 查询：加 reranker（cross-encoder / LLM），只在 top 20 上做，控制成本。
5. 检索评估：扩到几百条真实问题，做置信区间和分类型置信度；加“无答案”样本。
6. 运维：索引版本、灰度、缓存、监控召回率与工具错误率。

## Q8：LangChain / Dify / n8n 能带来什么？为什么还自己写？

- LangChain：生态、memory、retriever/tool 适配、可接多种模型；代价是抽象层多、版本变化快、排障成本高。
- Dify：可视化 workflow、应用管理、渠道发布，适合快速交付；代价是平台绑定和定制边界。
- n8n：低代码集成外部系统；适合把 `/ask` 接到工单、飞书、邮件，不适合做核心检索。
- 自己写：链路短、每一行可解释、可离线复现；适合面试展示与教学。

我的做法是核心保持 stdlib，`integrations/` 提供 LangChain / Dify / n8n 的参考适配；FastAPI 也是可选层，缺依赖时明确提示安装。这样既能讲清底层，也能展示集成能力。

## Q9：SQL 工具怎么防止被滥用？

当前实现：

- SQLite 以 `file:...?mode=ro` 只读 URI 打开；
- 只接受单条 `SELECT` / `PRAGMA`；去掉一个尾分号后仍含 `;` 直接拒绝；
- 拒绝双下划线标识符；结果最多 100 行；
- 工具异常转成 `ToolError`，不把数据库路径/堆栈暴露给模型。

生产还要加：

- 独立只读账号 / 只读副本，不用业务主库；
- 表、列、函数白名单（禁止 `ATTACH`、`load_extension`、危险 PRAGMA）；
- SQL AST 解析或代理层，限制扫描行数、超时、并发；
- 行级权限与审计日志；
- 自然语言 → SQL 的输出必须经过校验，不能把模型生成的 SQL 直接执行在主库上。

## Q10：为什么坚持标准库？代价是什么？

约束来自项目目标：离线、可复现、无隐藏依赖、面试能逐行解释。收益是启动快、部署简单、行为确定；代价是没有成熟分词器、ANN、异步、schema 校验和工具编排，性能和生态都有限。

如果这是生产项目，我会优先引入：向量库、全文检索、pydantic/FastAPI、真正的 LLM SDK、可观测性；但核心的“分块—召回—融合—工具—评估”链路仍然保持同样的接口。

## Q11：Hybrid 在 test 上和 Dense 持平，怎么解释“混合检索的价值”？

我不会把持平说成胜利。正确说法是：

- test 的 6 条语义型查询被 Dense 的领域同义词表完全覆盖，Dense R@5 已到 1.0，Hybrid 没有提升空间；
- test 的词面型 6 条，BM25 和 Dense 的 R@5 都是 1.0，但 BM25 的精确匹配仍是更可靠的排序信号；
- dev 上 Hybrid 的 MRR 与 nDCG 高于两个单路，说明融合在更困难的切片上有收益；
- BM25 语义型 R@5 只有 0.5000，说明单路在另一类查询上会明显掉，这就是保留混合的工程理由。

如果面试官追问“那为什么不用 Dense”，答案是：Dense 的语义能力来自一份人工同义词表，换领域会失效；BM25 不依赖这份表，二者是互补的保险。要证明混合在 test 上的收益，需要更大的、未参与调参的评估集，这也是下一步工作。

## Q12：怎么减少幻觉？

1. 工具优先：制度题必须 `kb_search`，答案里带 `doc_id + heading_path`；没有命中就明确说“知识库未找到”。
2. SQL 题要求聚合口径，不靠模型心算；比例题必须调用 `calculator`。
3. Agent 的 system prompt 明确“不要编造”；最终答案由工具观察生成或受其约束。
4. 评估里用 `expect_answer_contains` 检查事实，不只看“像不像”。
5. 生产加引用校验、答案与证据一致性检查、人工抽检和失败样本回流。

当前 MockModel 的答案直接摘自检索片段，这能证明链路，但不能证明真实 LLM 的忠实度；真实模型需要单独做 groundedness 评估。
